Why this project exists

Kids who play Roblox and want to make Roblox games have to learn Luau, and every route to it — YouTube, CodaKid, Outschool, Luablox — requires leaving Roblox and none of them is a game. The one in-game option, Scripting School, is single-player and has not been updated since 2026-02-12. Its 4.38M visits against a snapshot of 5 concurrent players is the shape of the opportunity: the demand is real, the retention is not.

What counts as "done"

v1 is done when a player who has never written a line of code can join, and within an hour have written a for loop, an if, and a function of their own — as real Luau, on a phone, with other players in the room — and come back the next day to room 9.

What is NOT in scope

  • Languages other than Luau. Teaching four languages is what diluted the incumbent.
  • loadstring, in any form. See D-001.
  • Selling lessons. Monetisation, if any, is cosmetic only.
  • Any room that cannot be solved without a keyboard.

How the game gets made

Pipeline

Codebot was started on 2026-09-17. The hardest part of it — a Luau interpreter written in Luau — was built and fully tested before Roblox Studio was opened once, because Roblox cannot run player-written code and the thing that replaces it does not need Roblox to exist. Everything the player sees is built by code at run time, so the whole game is readable text in git.

  1. IdeaLuqman asked for a Roblox game that teaches Luau. One incumbent exists, with 4.38M visits, single-player, and five people in it.01-idea.md
  2. DecideNo loadstring, so we write our own interpreter; real Luau syntax entered by tapping, because most Roblox play is on phones.06-decisions.md
  3. TokenizeCut the player's text into pieces, each knowing the line and column it came from.src/shared/Interpreter/Tokenizer.luau
  4. ParseTurn those pieces into a tree, so that inside the loop becomes something the program can say.src/shared/Interpreter/Parser.luau
  5. RunWalk the tree one statement at a time, pausing between each so the game can draw it.src/shared/Interpreter/Interp.luau
  6. RoomsThe curriculum as pictures, with a test that runs every room's own answer and checks it reaches the goal.src/shared/Rooms.luau
  7. BuildThe room, the robot, the camera and the panel, all generated by code at run time.src/client/
  8. TestEvery part that has no Roblox in it is tested from a terminal with Lune, Studio closed.tests/
  9. LookPress Play in Studio and read the screen. The only part of this game that cannot be tested.docs/shots/
  10. LogWhat was done, decided and learned in each session goes into the notes.log/
  11. RecordThis page, rebuilt from the notes, the screenshots and git.tools/docs/build_docs.py

Tools

Roblox and LuauThe engine. Chosen for free multiplayer, saves and an audience that is already there — none of which a website gives.
RojoKeeps the game as .luau files on disk instead of a binary place file, so it lives in git and can be read. rojo build makes a place with Studio closed.
LuneRuns the interpreter, the rooms and the code builder from a terminal, which is how everything below the screen is tested.

What the player sees

Screens

Screenshots from the game. Each carries the date it was taken: older ones show the game as it was then, and are kept as a record rather than replaced.

The first room

Room 1 offers three buttons and asks for one line. Everything a beginner needs to succeed once is on the screen and nothing else is.

Watching it run

The line being run is lit, the variables are listed underneath, and the robot moves one tile per step. This is the whole teaching mechanism.

When it goes wrong

Every error is a sentence pointing at a line. A beginner who cannot read the error is a beginner who stops playing.

The palette grows

Pieces arrive room by room, and the piece that is new in a room is drawn in the accent colour. That is the only tutorial the game has.

On a phone

The reason the palette exists. Nothing here needs a keyboard, and the layout is sized from the height of the screen rather than in fixed pixels.

01-idea.md · 7 sections

Idea

Problem

Millions of kids play Roblox and want to make Roblox games. To do that they have to learn Luau. Today they learn it from YouTube videos, paid outside courses (CodaKid, Outschool), or browser platforms (Luablox) — all of which require leaving Roblox, and none of which are a game.

Inside Roblox there is exactly one incumbent, Scripting School (TwoToned Studios, live since 2021). Its numbers, pulled from the Roblox games API on 2026-09-17:

MetricValue
Lifetime visits4,380,084
Favourites188,456
Concurrent players (one snapshot)5
Max players per server1
Last updated2026-02-12

Read together, those say two things. The demand is proven and large — 4.38M visits is not an accident. And retention is dead: maxPlayers: 1 means it is a single-player lesson reader with a 3D lobby around it. It uses none of what Roblox is actually for. People arrive, read, and never come back.

Proposed solution

A 3D puzzle game where you write real Luau to walk a robot through a room. Your code is the controller: there is no joystick, no jump button. You write move() and the robot moves one tile.

Other players are in the same room solving the same puzzle at the same time, and you can watch their robots run — and fail — beside yours. Rooms are ordered so each one introduces exactly one new idea: a line of code, then several lines in order, then a loop, then a variable, then a condition, then a function of your own.

The code is real Luau syntax, not blocks, so everything learned transfers directly to Roblox Studio.

Target users

SegmentNeedWhy they'd pick us
Roblox player, has never codedWants to make games, doesn't know where to startIt is a game, not a lesson. No account, no payment, no leaving Roblox
Roblox player part-way through a tutorialUnderstands print(), stalls at loopsRooms isolate one concept at a time and show it running
Parent / teacher looking for a coding activitySomething the child will choose to openSits where the child already is

Value / advantage

  • Same proven demand, opposite design. The incumbent proves people want this and is single-player, un-updated since February 2026, and holds nobody.
  • The multiplayer is the teaching. Watching another player's robot solve a room in three lines when yours took nine is the moment a beginner learns what a loop is for. That cannot happen in a single-player lesson reader.
  • It transfers. Real Luau syntax means the player leaves able to open Studio.
  • Custom 3D. Most Roblox developers cannot model; Luqman can. The robot and the rooms can look like nothing else on the platform.

Assumptions to validate

Side ideas (parking lot)

  • A room the player writes themselves and shares by code, so players teach each other.
  • A "ghost" replay of the shortest known solution, unlocked after you solve a room.
  • Scoring by lines used, so a solved room can still be improved — the thing that makes Human Resource Machine replayable.
  • Later languages beyond Luau. Deliberately not v1: the Luau-transfers-to-Studio promise is the differentiator, and diluting it is what the incumbent did.

02-planning.md · 8 sections

Planning

Scope

Must have (MVP)

  • to do A Luau interpreter written in Luau: tokenizer, parser, stepping evaluator
  • to do The subset of Luau listed under "Language subset" below, and nothing more
  • to do A code editor that works on a touchscreen: tap-to-build token palette + typing
  • to do Step-by-step execution — current line highlighted, variables panel, ~2 lines/sec
  • to do A grid room: floor tiles, walls, a robot, a goal tile
  • to do 8 rooms, each introducing exactly one new idea (see "Room ladder")
  • to do Up to 8 players per server, all in the same room, all robots visible
  • to do Progress and best-line-count saved with DataStore
  • to do Errors that a beginner can read — never a raw stack trace

Nice to have (v2)

  • to do Ghost replay of the best known solution, unlocked after solving
  • to do Player-authored rooms shared by code
  • to do Co-op rooms needing more than one robot
  • to do Script-a-turret wave mode
  • to do Game passes (cosmetic robot skins only — never sell the lessons)

Won't build

  • Languages other than Luau. The transfer-to-Studio promise is the differentiator.
  • loadstring. See D-001.
  • Tables, metatables, pairs/ipairs, string methods, coroutines — not in v1's subset.
  • Anything that needs a keyboard to complete.

Requirements

Functional

  • Player code can never touch anything outside the robot's built-in functions.
  • Execution can be stepped, paused and reset at any time.
  • Every error message names the line and says what to do, in plain words.
  • A room is solvable on a phone with no keyboard attached.

Non-functional

  • A running program must not be able to freeze the server: cap execution steps per run.
  • The interpreter runs on the client for responsiveness; the server re-runs the winning program before recording a best score, so a hacked client cannot fake it.
  • First room playable within 60 seconds of joining.

M1 — Tokenizer ✅ 2026-09-17

Goal: Turn the player's code into a list of tokens, each knowing where it came from. Done criteria:

  • done Names, keywords, numbers, text, operators and comments
  • done Two-character operators (==, ~=, <=, >=, ..) never split
  • done Every token carries its line and column
  • done Beginner mistakes explained in sentences, not symbol errors
  • done Runs and is tested with Studio closed

Learned: The friendly-error table turned out to be the most valuable part, and it cost almost nothing — a lookup of eight entries. A beginner who types != gets told what Luau uses instead, rather than "unexpected symbol", and that is the difference between carrying on and quitting.

M2 — Parser ✅ 2026-09-17

Goal: Turn the token list into a tree describing the shape of the program. Done criteria:

  • done The whole v1 subset from 02-planning.md and nothing beyond it
  • done if / while / numeric for / local function / calls / return / break
  • done Operator precedence correct, including and / or / not and right-associative ..
  • done A missing end names the line the block opened on, not the end of the file
  • done = used where == was meant is caught and explained

Learned: The first version reported a missing end at the end of the file. The message named the right line but the error's line number pointed at the player's last innocent line, which is what the editor would have highlighted. Naming a line in the text is not the same as pointing at it — both have to agree.

Dependencies: M1 Blockers: none

M3 — Stepping interpreter ✅ 2026-09-17

Goal: Run the tree one step at a time so the game can draw each step. Done criteria:

  • done step() advances one statement and reports the line it is on
  • done Variables readable from outside, for the variables panel
  • done Hard cap on total steps, so an infinite loop cannot hang the client
  • done A depth cap as well, so runaway recursion cannot blow the stack
  • done Robot built-ins injected by the caller, never global
  • done Runtime errors carry a line number and a plain sentence

Learned: Stepping is done with a coroutine, which keeps the evaluator as ordinary recursive code — a while loop in player code is a real while loop in the evaluator. A hand-rolled state machine would have bought nothing and cost every line's readability.

The sandbox is a consequence of the design rather than a feature bolted on: there is no global table inside a program at all, so game, require, getfenv and loadstring are not blocked, they simply do not exist. Five checks assert exactly that.

Dependencies: M2 Blockers: none

Phase 1 is complete. The interpreter is finished, is 152 headless checks, and has never needed Roblox Studio to be open.

M4 — Robot in a room ✅ 2026-09-17

Goal: A room in Studio with the interpreter driving the robot. Done criteria:

  • done Rooms defined as pictures in Rooms.luau, all eight of them
  • done RobotWorld.luau holds the rules — walls, facing, move, blocked, atGoal — with no Roblox in it, so they can be tested
  • done RoomView.luau builds the room and robot out of parts and animates the events
  • done Camera framed on the room, sized to fit the biggest one
  • done A panel with the room's brief, a code box, Run and Reset, a line highlight, a message line and a variables line
  • done The place builds with rojo build and needs nothing assembled by hand

Learned: Splitting the rules from the drawing paid for itself immediately. Because RobotWorld has no Roblox in it, a test could run every room's own intended solution and assert it reaches the goal — and it failed on two rooms straight away. The Wall turned into a wall and Your Own Move had a path its own answer could not walk. Both were rewritten before Studio was opened. Neither would have been found by reading, and finding them by playing would have cost an evening each.

A second bug the compiler could not catch: CodePanel had a field called highlight and a method called highlight. Lua looks the field up first, so panel:highlight(3) would have tried to call a Frame. Renamed the field to highlightBar.

06-decisions.md · 8 sections

Decisions

One decision = one entry. Never delete old entries — mark them Superseded by D-00X.
D-001 — Write our own Luau interpreter instead of using loadstring
  • Date: 2026-09-17
  • Status: active
  • Context: The game's whole premise is running code the player wrote. Roblox's loadstring is gated behind ServerScriptService.LoadStringEnabled, which defaults to false, exists only on the server, and which Roblox's own documentation recommends leaving off: feeding it a player-supplied string is textbook remote code execution.
  • Options considered:
OptionProsCons
A — enable LoadStringEnabledAlmost no work; full LuauAny player can run arbitrary code on our server. Not shippable
B — write an interpreter in LuauFully sandboxed; we control every stepReal work: tokenizer, parser, evaluator
C — block-based code compiled to our own opcodesSafe, no syntax errorsStops being Luau, so it no longer transfers to Studio
  • Decision: B.
  • Reason: Three things, in order of importance. It is the only safe option. It is better than loadstring for teaching, because an interpreter we own can pause on line 4, highlight it, show i = 3 and move the robot one tile — loadstring gives a black box that either works or throws. And it is the strongest portfolio artifact in the project: a tokenizer, a parser and a stepping evaluator with a test suite read well in git.
  • Consequences / trade-offs: We support a deliberately small subset of Luau and must say so honestly in the game. Every new language feature is work.
  • Reversible? No — the whole codebase sits on it.
D-002 — Real Luau syntax, entered through a tap-to-build token palette
  • Date: 2026-09-17
  • Status: active
  • Context: Most Roblox sessions are on phones and tablets. Asking a beginner on an iPad to type for i = 1, 10 do is where they quit. But block-based code does not transfer to Roblox Studio, which is the reason the player is here.
  • Options considered:
OptionProsCons
Typing onlySimplestUnusable for most of the actual audience
Blocks onlyTouch-friendly, no syntax errorsTeaches concepts, not Luau
Token palette producing real Luau textTouch-friendly and real syntaxMore UI work than either
  • Decision: A palette of tappable tokens (for, i, =, 1, do, move(), …) that assembles into real Luau text on screen, with a keyboard accepted as an alternative into the same editor.
  • Reason: It keeps the transfer-to-Studio promise while remaining playable with one thumb. The player reads genuine Luau from the first minute even though they never typed a character.
  • Consequences / trade-offs: The palette must be context-aware to stay short, which is real design work. Syntax errors are rarer but not impossible.
  • Reversible? With difficulty — the editor is a large piece of UI.
D-003 — Multiplayer, everyone in the same room
  • Date: 2026-09-17
  • Status: active
  • Context: The incumbent, Scripting School, has 4.38M lifetime visits and maxPlayers: 1. It proves the demand and fails to hold anyone.
  • Decision: Up to 8 players per server, all working the same room, every robot visible while it runs.
  • Reason: It is the only thing Roblox offers that a website cannot, and it is the incumbent's exact weakness. It is also pedagogy: seeing another player's robot finish a room in three lines when yours took nine is how a beginner discovers what a loop is for. A lesson cannot do that.
  • Consequences / trade-offs: Four robots at once risks visual noise; other players render faded, with a toggle to hide them.
  • Reversible? Easily — it can be turned down to a solo server.
D-004 — Interpreter runs on the client, server re-runs to confirm a score
  • Date: 2026-09-17
  • Status: active
  • Context: Stepping code must feel instant, which argues for the client. But a client can be modified, and best-line-count is a leaderboard number.
  • Decision: Execute on the client for responsiveness. When a player claims a solve, send the program text to the server, which runs the same interpreter and only then records the score.
  • Reason: Responsiveness where it is felt, authority where it is needed. The interpreter is shared code, so this costs nothing extra.
  • Consequences / trade-offs: The server needs its own step cap so a submitted program cannot hang it.
  • Reversible? Easily.
D-005 — The room is built on the client for now
  • Date: 2026-09-17
  • Status: active
  • Context: M4 needed a room on screen. A room can be built by the server into Workspace, where everyone shares it, or by each client into its own Workspace.
  • Decision: Build on the client, in RoomView.create.
  • Reason: While every player has their own robot and their own attempt, there is nothing to agree on, and a client build keeps M4 to one file with no networking.
  • Consequences / trade-offs: This is exactly what M7 has to undo. When players share a room, the room itself becomes the server's and only the robots stay per player. Recorded here so that M7 knows where to look rather than rediscovering it.
  • Reversible? Easily — RoomView takes the parent it builds into.
D-006 — Rooms are pictures, not coordinates
  • Date: 2026-09-17
  • Status: active
  • Context: A room needs walls, a start, a facing and a goal. That can be a list of coordinates or a drawing made of characters.
  • Options considered:
OptionProsCons
CoordinatesPrecise, no parsingUnreadable in a diff; editing means arithmetic
A picture made of #, ., R, GReadable at a glance, editable by moving one characterHas to be parsed; rows must be kept the same width
  • Decision: Pictures, parsed by RobotWorld.create.
  • Reason: The curriculum will be edited far more often than it is written, and a room you can see in the file is a room whose mistake you can see in the file. The width risk is covered by a test asserting every room is rectangular.
  • Consequences / trade-offs: One character per tile, so a tile can carry no extra information. When a room needs more than walls and a goal, this has to grow.
  • Reversible? Easily — only RobotWorld.create reads the picture.
D-007 — A profile that failed to load is never saved over
  • Date: 2026-09-17
  • Status: active
  • Context: A player joins, the server reads their progress from the DataStore, and later writes it back. If the read fails — DataStore outage, throttling, Studio without API access — the server is holding an empty profile for someone who may have solved every room.
  • Options considered:
OptionProsCons
Save anywaySimple; the session's work is never lostA failed read followed by one save erases everything the player had
Refuse to save unless the read succeededA bad read can only ever cost one sessionThe session's work is lost when the read failed
  • Decision: A session carries a loaded flag. Saving is refused unless it is true.
  • Reason: The two failures are not the same size. Losing one session is a bad evening; overwriting a finished profile with an empty one is unrecoverable and looks, to the player, exactly like the game deleting their work.
  • Consequences / trade-offs: A player whose read failed plays a session that will not be kept, and the game tells them so rather than letting them find out.
  • Reversible? Easily, and should not be.
D-008 — Profile keys are strings
  • Date: 2026-09-17
  • Status: active
  • Context: A profile maps a room number to a best line count.
  • Decision: The key is the room number as a string: { best = { ["1"] = 3 } }.
  • Reason: A DataStore stores JSON. A table written with number keys is stored as an object and comes back with string keys, so a profile written as { [1] = 3 } is not the profile that returns. Using strings on both sides means saving and loading cannot disagree. Progress.sanitize accepts either, so anything written by an earlier version still loads.
  • Consequences / trade-offs: Every lookup goes through tostring, which is why the module has bestFor and isSolved rather than letting callers index best directly.
  • Reversible? No, not without a migration.

Patterns in use

A module that loads both in Roblox and in Lune

Roblox resolves a require through the data model (script.Parent.X); Lune resolves it as a file path ("./X"). The script global does not exist in Lune, which gives a clean way to branch:

local Tokenizer = if script then require(script.Parent.Tokenizer) else require("./Tokenizer")

Verified on 2026-09-17: under Lune, typeof(script) is nil, require("./Mod") resolves, and require("@self/Mod") does not.

Errors are sentences, not symbols

Every error the interpreter produces is { message, line, col } and is returned, never raised — the caller is a game that has to draw the problem on screen. The message is written for someone who has never coded: "This piece of text is missing its closing " mark.", not "unexpected symbol near '\"'". The tokenizer also keeps a small table of mistakes borrowed from other languages (!=, &&, ||, {, ;) and answers each with the Luau equivalent.

Syntax errors are raised, then caught once

The parser is recursive descent, so a failure can happen at any depth. It raises a table carrying a __syntaxError marker and Parser.parse catches it with pcall. The marker matters: anything raised without it is a genuine bug in the parser and is re-raised rather than being reported to the player as bad code. A game that blames the player for our mistakes is worse than one that crashes.

Never throw across a coroutine boundary

Lune converts a table thrown out of a coroutine into a string — coroutine.resume returns false, "runtime error: table: 0x..." — so the message and line are lost. Roblox hands the table back intact. Code that relies on the Roblox behaviour therefore passes in Studio and fails in the tests, or worse, the other way round.

The interpreter avoids the question: the coroutine body wraps itself in pcall and stores the caught error on the machine, where step() reads it. Yielding from inside a pcall is fine in Luau, so stepping is unaffected. Verified 2026-09-17.

The interpreter never sees Roblox

Nothing under src/shared/Interpreter/ may touch a Roblox API. That is what lets the hardest part of the game be built and tested from the terminal, and what makes the test suite fast.

The room's shell

Each room builds its own enclosure in RoomView.buildShell — a floor slab, four walls, a lit stripe at eye height and a soffit of light fittings — sized from that room's grid, so a room is somewhere rather than a set of tiles in a void. Two things about it are not obvious:

The soffit is a ring, not a ceiling. The camera looks down into the room from well above the wall tops, so a closed ceiling would cover the entire game with a grey rectangle.

The fittings run along whichever way the room is longer. Room 4 is thirteen tiles wide and three deep; spreading the lamps down the short side put them all at the two far ends and left the hall itself dark. PointLight.Range maxes out at 60, which is only just enough to reach the floor from a soffit thirty studs up.

DataStore in Studio

DataStoreService only works when the place is published and Game Settings → Security → Enable Studio Access to API Services is on. Until then the server logs no DataStore available, the game plays normally, and the message after a solve ends with "(Progress is not being saved.)" — deliberately, because a player silently losing progress is worse than a player being told.

Nothing from a client is believed

SubmitSolution receives a room number and a string. Before either is used it is checked for being the shape it claims to be, the room must exist, the room must be unlocked for that player, and a cooldown must have passed. Only then does the server run the code — with the same Solution.run the client used, so there is one definition of solved rather than two. Running a stranger's program is safe because the interpreter hands it nothing but the robot's own actions and stops at a step cap.

The project record

docs/index.html is generated from this knowledge base by tools/docs/build_docs.py and published to https://luqman-docs.netlify.app/codebot/. It must be rebuilt and republished whenever the game changes, which is the standing rule for every one of Luqman's games.

Codebot's copy differs from the other games' in two ways. Its screenshots cannot be taken by a script, because Studio is not a browser — they are captured by hand and dropped into docs/shots/, and any named picture that is not there yet shows as a labelled gap, so the GALLERIES list doubles as the list of pictures still to take. And its header_comment() understands Luau's -- and --[[ ]] comments, which the shared engine did not.

The cover's check count is produced by running the suites, not by counting lines that look like checks, so it cannot drift away from the truth.

The one thing that makes it different from an ordinary evaluator is that it can stop between statements and be resumed later: local machine = Interp.create(ast, { builtins = ... }) machine:step() -- runs one statement, says which line it was machine:step() -- runs the next one That is the whole teaching mechanism. The game steps it about twice a second, highlights the line it reports, and animates the robot doing it. A program that ran all at once would show a beginner nothing. Stepping is done with a coroutine. The evaluator below is written as ordinary recursive code — a while loop really is a while loop — and simply yields at each statement. Hand-rolling a state machine to get the same effect would make every line of this file harder to read for no gain. Two things are deliberately not here: * No globals. move() and blocked() are handed in by whoever creates the machine. Player code can reach nothing we did not give it, which is what makes running a stranger's code safe. * No Roblox. This file can be run and tested from a terminal.
src/shared/Interpreter/Parser.luauParser — step 2 of 3 in the interpreter. The tokenizer gave us a flat list of pieces. The parser works out the shape those pieces make: what is inside what. for i = 1, 3 do move() end -> ForNumeric (i, from 1, to 3) body: Call (move) A flat list cannot be run, because "inside the loop" is not a thing a list can say. A tree can. This is the step that turns an order of words into a structure with a body, and it is also where we find out that a program is nonsense before anyone tries to run it. Nothing here touches Roblox, and it does not require the Tokenizer either — it just reads a list of tables. That is what lets it be tested from a terminal. The node kinds it produces, and the fields each one carries: Number value String value Boolean value Nil Name name Binary op, left, right Unary op, expr Call name, args Local name, expr Assign name, expr If branches ({ cond, body }), elseBody While cond, body ForNumeric var, from, to, step, body Function name, params, body Return expr Break ExprStat expr Every node also carries the line it started on, because the game highlights the line it is currently running.
src/shared/Interpreter/Tokenizer.luauTokenizer — step 1 of 3 in the interpreter. Turns the player's code, which is just one long string of characters, into a flat list of tokens: the smallest pieces that still mean something. "for i = 1, 3 do" -> for | i | = | 1 | , | 3 | do It does not care whether the code makes sense. "end end end end" tokenizes perfectly happily. Deciding whether a sequence of tokens is a real program is the Parser's job, and actually running it is the Interpreter's. Every token carries the line and column it came from, because the player is a beginner and every error we show them has to point at a place in their code.
The parts you can see

Built by code at run time. Nothing in this game was assembled by hand in Studio.

FileWhat it does
src/client/CodePanel.luauCodePanel — where the player writes, and where the running line is shown. The code is built by tapping pieces from the palette, and the panel shows the result as ordinary Luau text. Nothing here is a block or a picture of code: what is on screen is what the player would have typed, which is the promise the whole game rests on. A TYPE button swaps the display for a text box, for anyone at a keyboard who would rather write it out. Switching back turns the typed text into pieces again, so DELETE still removes a whole word rather than a letter. Everything is sized from the height of the screen, because this is played on phones as well as desktops and a layout in fixed pixels only ever fits one of them.
src/client/PaletteView.luauPaletteView — the buttons the player taps to write code. Laid out by hand rather than with a UIGridLayout, because a grid would give "move()" and "," the same width and the palette would read as a wall of identical tiles. Each button is as wide as its own word, wrapped into rows, the way words sit on a page. Pieces that are new in this room are drawn in the accent colour. That is the entire tutorial for a room: the new button is the lesson.
src/client/RoomView.luauRoomView — the part you can see. Builds a room out of parts from the same picture the rules were read from, puts a robot on it, points the camera at it, and plays back the events the world produced. It holds no rules of its own. Where the robot is was decided by RobotWorld before this file was asked to move anything, which is why the rules could be tested without a screen. If the robot appears somewhere wrong, the bug is here; if it goes somewhere wrong, the bug is there. Everything is built on the client. That is fine while each player has their own room, and is the one thing that has to change for M7, when the room becomes shared and the server builds it.
src/client/Theme.luauTheme — every colour and size in one place. Sizes are deliberately generous. This is a game played on phones and read by people who are concentrating on unfamiliar words; small text is not a style choice here, it is a way of losing players.
src/client/init.client.luauThe client. Loads a room, draws it, and runs whatever the player wrote. The loop in run is the game: step the interpreter -> highlight the line it just ran -> play whatever the robot did -> pause, and do it again Solving a room is decided twice. Here, so the player is told immediately; and again on the server, which runs the same code through the same interpreter before writing anything down. The client's answer is for the player's eyes, the server's answer is the one that counts.
src/server/init.server.luauThe server. It owns one thing: what a player has actually solved. Two rules shape the whole file. Nothing a client says is believed. A client sends the code it thinks solves a room; the server runs that code itself, with the same interpreter and the same room, and only writes a score down if the robot really reaches the goal (D-004). Running a stranger's program is safe because the interpreter hands it nothing but the robot's own actions, and it stops at a step cap. A profile that failed to load is never saved over. If the DataStore is unreachable when a player joins, they play the session with a blank profile — but that blank profile must not be written back, or a moment of DataStore trouble would erase everything they had done. Saving is only ever allowed for a profile we know we read.
